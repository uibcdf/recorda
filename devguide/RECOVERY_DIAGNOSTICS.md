# Explicit recovery diagnostics — experimental source integration

Owned by [uibcdf/recorda#16](https://github.com/uibcdf/recorda/issues/16), under
the wider support-library review in `uibcdf/recorda#2`.

Recorda can emit two catalog diagnostics when persistence fails while a native
exception is already propagating: operation completion
(`RECORDA-RECOVERY-OPERATION-001`) and session completion
(`RECORDA-RECOVERY-SESSION-001`). Native exception identity, cause and traceback
remain intact. The existing fixed note remains available even if diagnostic
delivery fails, is filtered or reenters recovery. Scientific failures with normal
persistence, successful work and persistence faults without an active native
exception do not emit these recovery diagnostics. Existing I/O errors still
propagate in that last case.

## Explicit activation

The new scoped APIs are implemented in SMonitor source
`6feac9728cc35d57cbc92f284d7040d7f04cb35b`, but its latest checked public release,
0.18.0, does not provide them. This adapter is a controlled development route;
there is no supported public provider version or install extra selected yet.
Install that exact provider checkout in an isolated development environment
with its declared build prerequisites, or use the pinned source lane below.
Do not substitute a branch name or attach these APIs to the old release.

```python
import recorda
from recorda.integrations.smonitor import SMonitorRecoveryDiagnostics

diagnostics = SMonitorRecoveryDiagnostics()
handle = recorda.start("controlled-run", path="run.jsonl", recovery_diagnostics=diagnostics)
try:
    # Execute the explicitly recorded operations here.
    pass
finally:
    result = handle.stop()
```

Create the adapter before activating the session. An absent/older provider fails
on explicit adapter import before recording. Construction registers the Recorda
catalog without selecting SMonitor's level, profile, handlers or capture policy.
`import recorda`, ordinary recording and independent inspection do not import
SMonitor. Default `recovery_diagnostics=None` keeps the fixed notes only.

## Payload and failure contract

The adapter receives a fixed code, session UUID and, for operation recovery, the
operation UUID. It enters SMonitor's metadata-only diagnostic scope and emits
from the registered catalog. It never receives scientific objects, native or
storage exceptions, arguments, results, names, journal paths or reference details.
Recorda identities use `recorda_session_id` and `recorda_operation_id` in approved
extra fields; SMonitor's own runtime identities are not overwritten.

SMonitor may retain application-approved safe facts and configured runtime IDs;
their contents remain the application's responsibility. This integration does
not erase or prevent diagnostics already generated by another producer, and
does not wrap the scientific target in `@signal`. Filters and coalescing still
govern SMonitor delivery. An emitted event is not a durable journal completion.
A complete final journal line followed by an fsync failure cannot tell a later
reader whether the durability request succeeded; no new durability certification
is implied by either a diagnostic or inspection.

`recovery_diagnostics` may also be a trusted synchronous callable accepting
`(code, *, session_id, operation_id=None)`. Its faults, including interrupts,
cannot replace the already propagating native failure. A context-local guard
suppresses recursive sink delivery while retaining notes on nested failures.
The callback must complete synchronously; async/generator sinks are rejected.
Callers remain responsible for arbitrary actions performed by their own sink.

## Qualification and remaining work

Ordinary CI tests the installed core without activating this adapter. The separate
Linux Python 3.11–3.14 lane tests installed Recorda with the exact SMonitor source
above and published pytest-receptor 1.1.0. It is source-provider qualification,
not a published-provider certificate. Locally, use a Python 3.14 environment
containing that published receptor and the SMonitor checkout at the exact SHA:

```bash
RECORDA_TEST_SMONITOR=1 PYTHONDONTWRITEBYTECODE=1 \
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONPATH=/path/to/pinned/smonitor \
python -m pytest -p pytest_receptor.plugin --receptor=llm
```

The receiving tests cover both advice sites, before-line/fsync faults, inherited
producer context, safe event contents, native failure identity/cause/traceback,
fixed-note fallback, recursive delivery, filtered delivery, interleaved sessions
and threads, import isolation and application-policy preservation.

Select and qualify new published provider artifacts before declaring a supported
optional dependency or promoting ecosystem adoption. That remains in
`uibcdf/recorda#2` / `uibcdf/recorda#3`. Inspection presentation (#14), linking
provider diagnostics (#15) and ArgDigest configuration adoption remain separate.
